# CloudNativePG FailoverQuorum bounded experiment

**No operator defect was established. The only fault attempt failed in the harness and did not delay quorum delivery.** Both fresh learning runs and the matched no-fault test-image control passed independent API, SQL, network and client checks. The intended stale-W=2 hypothesis remains unexercised; this result does not refute it.

The experiment retained pinned CloudNativePG `96cb6b05aea5f76ddac43d21e0f178e0a8b1b331`, source snapshot `5672f43a59c921f9e15c9ce4be28cf824dee9714`, ten reconciliation workers, three dedicated PostgreSQL worker nodes, the fixed native images, the vanilla instance-manager image, and frozen workload/plans/oracles. The control stage already running at handoff was resumed without duplication. All result trees were copied in full and every file checked against VM SHA256 values before inspection.

All **491 acknowledged transactions** were verified with exact payloads on all three final instances. All **646 successful reads** passed payload, monotonicity and causal acknowledgement/possible-write bounds. Complete terminal ledgers and every ambiguous write were retained. The controls proved required ANY 2 before writes, accepted ANY 1 and W1/N2 metadata, a remote_apply witness on B, A missing that witness, physical network detach/restore at the original IPv4/IPv6 addresses, denial throughout the observation window, and healthy recovery with current settings. R1+W1 is not greater than N2, so this unavailability is expected. Every failed client attempt overlapped the recorded isolation/recovery interval and targeted its own Cluster read/write Service. Retained errors were connection refusal, connection timeout, no route to host, network unreachable, and one five-second write query deadline; failed writes remain ambiguous. Read success gaps were 180.037–211.540 seconds and acknowledgement gaps 181.235–216.250 seconds under the deliberate isolation and recovery; those gaps alone are not operator defects.

The controller remained on the control plane with one unchanged Pod UID per run, no controller restarts, stable leadership, and an actual ten-worker startup record. The isolated PostgreSQL primary containers restarted 3, 4 and 3 times. Kubelet events record liveness-triggered restarts during isolation; historical instance-manager logs for every later exit were not retained, so their complete root causes are not claimed. The second learning run safely promoted witness-bearing B after network restoration with current R2/W1/N2 acceptance and a primary-lease handoff. No stale A was promoted in these controls. Two raw binary-hash alarms remain unchanged and are bound to the known learn/test binary identities. One operator leader-lease resourceVersion conflict is retained in both log copies; subsequent renewals prove unchanged leadership. No alarm or oracle mask was edited.

Fault attempt 1 armed the pause at **12:19:10.950270 CST (18:19:10.950270 UTC)**. It recorded **zero actual holds**. The selected plan requests beforeAPIServerRecv callbacks only for Cluster; the frozen API client filters callbacks using those trigger observation points. A quorum pause scope alone does not enable its API callback. Current W1 metadata was delivered after arming, and all **35 observed native quorum Gets** returned its exact UID/resourceVersion `1836`, rather than old W2 resourceVersion `1782`. The operator logged **16 native R1/W1/N2 denials** during the **121.449-second** observation; all 57 SQL samples kept A in recovery without the acknowledged witness.

At **12:22:09.334620 CST (18:22:09.334620 UTC)**, resume attempted to send on the unused unbuffered pause channel. No resume completion or coordinator completion followed. The channel-send diagnosis is an inference from the exact frozen source and arm/resume-attempt/no-hold/no-resume-done evidence, not a goroutine stack dump. Network restoration completed, but recovery did not finish before the parent’s **900-second deadline**. The workload and diagnostic/automatic cleanup commands were cancelled. No final Sieve verdict, generic fault proof, complete client ledgers or all-instance final SQL audit was emitted for this attempt. These missing artifacts are coverage limits, not passing checks or proof of preserved fault-run acknowledgements.

The strict physical auditor rejected the attempt because a real hold/release was absent. Six mutations of the failed-schedule diagnosis—missing arm, missing resume attempt, wrong quorum UID, missing current API receipt, missing native candidate proof and missing current cache Get—were rejected using copies of the evidence. Positive hold/release mutation tests cannot validate a hold that never existed. Earlier review attempts, parsing corrections and cancelled diagnostics are preserved alongside the final reviews.

Exactly **four workload executions and one new fault attempt** were used, within limits of six and two. There were no automatic repeats. The second matched pair was reserved for a meaningful physically verified failure; this attempt did not qualify, so neither control 2 nor fault 2 launched. The frozen plan and workload were not repaired or changed to obtain a different result. A future experiment needs a separately reviewed schedule that actually observes its quorum API delivery and can release without an unconsumed channel send.
