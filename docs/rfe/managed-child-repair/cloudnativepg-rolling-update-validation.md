# CloudNativePG rolling configuration reliability experiment

No new operator defect was verified. Both physical fault attempts preserved every acknowledged write, reached the latest configuration on all three instances, and recovered after one ordinary primary-restart interruption per client stream. The delayed-read run had slightly longer success gaps than the matched control; that single-run timing difference is unconfirmed and is not classified as a reproducible additional outage or operator bug.

A success gap measures the interval between the successful completion before an interruption and the next successful completion. It includes the first recovered request's latency; the acknowledgement gap is not a claim that connections were unavailable for its entire duration. There were no five-second subprocess timeouts. Every failed write remains ambiguous, even though these particular final datasets contained none of the ambiguous IDs. Failed connections are not counted as acknowledged data loss.

The workload starts three healthy owned instances, independently verifies required synchronous replication (`any`, one standby, `dataDurability: required`) and effective `remote_apply`, and starts independent read and numbered-write streams through the rw Service. Each write uses `SET LOCAL synchronous_commit='remote_apply'` and requires a successful psql exit plus an exact receipt after COMMIT. Both streams preserve every attempt, wall and monotonic timestamps, deadline, output, result and terminal record. A ten-second healthy warmup precedes max_connections 100 → 120 → 140, with a four-second sleep between the two updates and no wait for the first rollout to finish. In all three controls, two instances were Ready immediately before the latest update was accepted, independently confirming overlap.

The pinned API defaults `primaryUpdateMethod` to `restart`. Actual controls and faults show replacement of replica Pods and an unchanged primary Pod UID with a changed postmaster start time. The primary restarts in place. Plans therefore use accepted Cluster and informer events, without requiring Pod deletion as a configuration trigger. Final SQL verifies 140, no pending restart, changed postmaster start times on all instances, two recovery roles, one primary, effective synchronous settings, and every acknowledged ID/payload on every instance after clients stop. A thirty-second healthy observation follows convergence. All **1,279 acknowledged writes** passed the final checks. The additional continuous-read audit checked **1,657 successful reads**: no count or maximum decreased, no bad payload was reported, and count/maximum bounds included writes acknowledged before the read began.

The delayed-read attempt physically held a successful ClusterReconciler cache Get returning **120**, generation 2, resourceVersion `1307`, for **5.431570 seconds**. During that hold the informer received the exact accepted **140**, generation 3, resourceVersion `1321`, on the same Cluster UID. The coordinator then released the read. Its returned object, reconciler, error status, API versions, hold and release are independently bound to the raw logs. Four mutated-evidence negative controls were rejected. The native Go serializer omits four zero/default spec fields; the supplemental auditor verifies those specific pinned `omitempty` declarations and otherwise requires exact spec, UID, generation and resourceVersion agreement. This does not change oracle masks or raw evidence. The generic missed-state verifier does not support after-read pauses; its original physical verdict remains false alongside the successful supplemental proof.

All 21 reads and 17 writes overlapping the hold succeeded. The later interruption began about 35 seconds after release, around the normal primary restart. Its read and acknowledgement gaps exceeded the matched control by **0.523 s** and **0.356 s**. There was no extra interruption episode or data/configuration failure. No confirmation was spent on this small timing difference; reproducibility is unresolved.

The controller-restart attempt proves deletion of controller UID `5f00e41a-5dd1-4f30-b892-40863eed76d7` and a distinct Ready replacement `3de8307f-ef47-4b1a-ace6-922722952167` after the latest update. Both the generic verifier and independent API audit pass. The coordinator's full action lasted **13.311621 seconds**; all 51 reads and 39 writes overlapping it succeeded. The leader lease changed to the new Pod with exactly one transition. Three retained native cancellation entries belong to one reconciliation during recorded shutdown; the replacement converged. Its later ordinary primary-restart gaps were shorter than the matched control.

All **eight raw alarms** remain: six native learn/test binary-hash differences, one completed client Pod CPU-status difference, and one expected leader-lease transition. Each is independently classified in the results. The CPU alarm concerns observed Pod status; declared requests stayed 20m CPU and 32Mi memory per client container, both containers exited successfully, and complete ledgers were retained. Raw Sieve verdicts remain failing because these alarms remain present. They are separate from the passing application invariants and physical fault audits.

The first learning workload failed before configuration updates because Python 3.14 formatting introduced exception syntax unsupported by the operand Python. Its whole failed tree is preserved. A public CLI regression failed before the fix and passed afterward, as did a standalone probe in the unchanged operand image. A client-specific Python 3.9 formatting target fixes the syntax. Fresh controls were then learned; no native image was rebuilt. Interrupted upload, failed launch preflight, failed supplemental reviews, intermediate reporting corrections and the partial upload are also preserved and indexed.

Exactly **two of four permitted fault attempts** were used, with no confirmations or automatic repeats. There were six actual workload executions: one failed initial learning workload, two successful learning workloads, one matched no-fault run and two faults. Two standalone operand-runtime diagnostics are separate. Test CLIs were bounded at 900 seconds, the two-baseline learning CLI at 1800 seconds, control services at 3000 seconds and fault services at 1200 seconds. No fault was launched before independent control verification.
